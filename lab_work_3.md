ER-діаграма бази даних «Бібліотека»
Завдання 1. ER-діаграма повної схеми

База даних бібліотеки містить дві вимірні таблиці (books, readers) та одну фактову таблицю (loans).

erDiagram
    books ||--o{ loans : "includes"
    readers ||--o{ loans : "borrows"

    books {
        INTEGER id PK
        TEXT title
        TEXT author
        INTEGER publication_year
        TEXT genre
        INTEGER copies_count
    }

    readers {
        INTEGER id PK
        TEXT last_name
        TEXT first_name
        TEXT email
        TEXT registration_date
    }

    loans {
        INTEGER id PK
        INTEGER book_id FK
        INTEGER reader_id FK
        TEXT loan_date
        TEXT return_date
    }

Завдання 2. Тип кожного зв'язку

1. Зв'язок books — loans: 1:N.

Одна книга може бути видана багато разів у різні дати або різним читачам, тому вона може відповідати багатьом записам у таблиці loans. Кожен запис у loans посилається на одну конкретну книгу через зовнішній ключ book_id.

2. Зв'язок readers — loans: 1:N.

Один читач може брати багато книг і мати багато записів у журналі видач. Кожен запис у таблиці loans стосується одного читача, на якого вказує зовнішній ключ reader_id.

Отже, обидва зв'язки мають тип 1:N. Фактова таблиця loans пов'язує книги та читачів і зберігає інформацію про видачу та повернення книг.

Завдання 3. Первинні й зовнішні ключі
Таблиця books
Первинний ключ (PK): id.
Зовнішні ключі (FK): відсутні.
Таблиця readers
Первинний ключ (PK): id.
Зовнішні ключі (FK): відсутні.
Таблиця loans
Первинний ключ (PK): id.
Зовнішній ключ (FK): book_id → books.id.
Зовнішній ключ (FK): reader_id → readers.id.

Первинний ключ однозначно ідентифікує кожен запис таблиці. Зовнішні ключі забезпечують зв'язок записів журналу видач із відповідними книгами та читачами.

Завдання 4. Додавання ще однієї сутності

До предметної області бібліотеки можна додати сутність publishers — видавництва.

Нова таблиця publishers міститиме такі стовпці:

id — первинний ключ;
name — назва видавництва;
city — місто, у якому розташоване видавництво.

У таблицю books можна додати стовпець publisher_id, який буде зовнішнім ключем і посилатиметься на publishers.id.

Зв'язок між publishers і books матиме тип 1:N, оскільки одне видавництво може видати багато книг, а кожна книга в цій моделі пов'язана з одним видавництвом.

Ескіз нового зв'язку:

erDiagram
    publishers ||--o{ books : publishes

Завдання 5. Порівняння з прикладом хімчистки

Моя ER-діаграма має таку саму основну структуру, як діаграма хімчистки з навчального прикладу. Обидві моделі складаються з двох вимірних таблиць та однієї фактової таблиці, яка містить два зовнішні ключі.

У моїй схемі вимірними таблицями є books і readers, а фактовою — loans. Обидва зв'язки (books — loans і readers — loans) мають тип 1:N. Вимірні таблиці не пов'язані безпосередньо, а взаємодіють через фактову таблицю loans.

Запитання
1. Чим концептуальна модель відрізняється від логічної, а фізична — від логічної?

Концептуальна модель описує предметну область на загальному рівні: які сутності існують і як вони пов'язані між собою. Вона не заглиблюється в технічні деталі зберігання даних.

Логічна модель визначає таблиці, стовпці, первинні й зовнішні ключі та типи зв'язків. Вона докладніше описує структуру даних, але не залежить від усіх особливостей конкретної СУБД.

Фізична модель показує, як логічну структуру реалізовано в конкретній СУБД: визначає конкретні типи даних, обмеження, індекси та інші технічні параметри.

2. Чому зв'язок M:N потребує окремої таблиці?

Зв'язок M:N означає, що багато записів першої таблиці можуть бути пов'язані з багатьма записами другої. Один зовнішній ключ у будь-якій з основних таблиць не може повноцінно представити всі такі зв'язки без дублювання даних або порушення нормальної структури.

Тому створюють окрему проміжну таблицю, яка містить зовнішні ключі обох таблиць. Кожен рядок цієї таблиці представляє один конкретний зв'язок між двома записами. У бібліотеці таблиця loans пов'язує книги з читачами через записи про видачу.

3. Що означають ||, o{ і |{ у Mermaid ER-діаграмах?
|| — рівно один.
o{ — нуль або багато.
|{ — один або багато.

Рядок A ||--o{ B читається так: кожен запис B пов'язаний рівно з одним записом A, а один запис A може бути пов'язаний із нулем, одним або багатьма записами B.
